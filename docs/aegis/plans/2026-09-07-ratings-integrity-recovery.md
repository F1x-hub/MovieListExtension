# План: восстановление рейтингов и предотвращение повторного исчезновения фильмов

## Goal

Восстановить восемь подтверждённо повреждённых документов фильмов и обеспечить
целостность `ratings → movies` независимо от версии клиента, очистки метаданных,
повторной доставки событий и параллельного изменения оценок.

Статус: только план. Код, правила, облачные функции и данные этим документом не изменены.
Запрос пользователя на план не является разрешением на запуск описанных миграций.

## Architecture

- `ratings` хранит пользовательские оценки; эти записи сохраняются при восстановлении.
- `movies` хранит метаданные и производные агрегаты для запросов страницы рейтингов.
- Целевая модель: сервер владеет записью оценок и расчётом агрегатов; клиент отображает
  подтверждённый результат и локальное состояние ожидания.
- Один серверный модуль пересчёта используется сохранением, триггером и восстановлением.
- Метаданные не могут удалять, заменять или сбрасывать поля общего рейтинга.
- Страница продолжает читать `movies`; отдельный полный каталог из `ratings` в UI не создаётся.
- Периодическая сверка обнаруживает и исправляет дрейф, но не заменяет защиту записи.

## Tech Stack

Chrome MV3, vanilla JavaScript, Firestore, Firebase Cloud Functions v2, Admin SDK,
существующие Node-тесты; для правил и конкурентных сценариев — Firebase Emulator Suite.
Перед реализацией проверить актуальные API через Context7, а при его недоступности —
официальную документацию Firebase. Не добавлять зависимости без проверки существующих.

## Compatibility Boundary

Сохранить оценки, отзывы, короткие комментарии, избранное, авторов, канонические ID,
редактируемость старых random-ID записей и существующую дедупликацию пользователей.
Не удалять дубли оценок в рамках этого ремонта. Не менять дизайн и фильтры страницы.
Номер версии не повышать автоматически; коммиты автоматически не создавать.

Нельзя одновременно сохранить неограниченные записи старых клиентов и гарантировать
серверное владение агрегатами. Поэтому переход проходит двумя совместимыми релизами,
после чего устаревшим клиентам явно требуется обновление. Запрет прямой записи нельзя
включать до выпуска нового пути сохранения: иначе старая общая транзакция откатится
вместе с пользовательской оценкой.

## Verification

Главный инвариант: каждому каноническому movieId с допустимой эффективной оценкой
соответствует один документ `movies/{movieId}` с правильными агрегатами и датой.
Проверять не только наличие документа, но также типы, значения, полноту и доступность
через реальный запрос страницы. Успешный build или тест сортировки этого не доказывает.

## 3. Этап B — единый расчёт и безопасное восстановление восьми фильмов

Файлы: `functions/ratingAggregation.js`, новый `functions/ratingProjectionService.js`,
новый `scripts/repair-rating-projections.cjs`, `tests/ratingProjectionService.test.cjs`.
Почему: старый backfill и клиентские счётчики не должны задавать разные результаты.

1. Закрепить тестами текущую семантику `selectUniqueMovieRatings`: приоритет canonical-ID,
   затем дата и стабильный ID; numeric/string movieId приводятся к одному ключу.
2. Один чистый расчёт возвращает count, sum, округлённый average, flags и дату из реальных
   событий. Недопустимые строки диагностировать; изменение политики их учёта выделить
   отдельно, не маскировать под восстановление.
3. Определить дату числовой оценки отдельно от даты правки отзыва: text-only обновления
   не должны менять порядок фильмов после очередной сверки. Для новых операций хранить
   серверную дату изменения оценки; для старых использовать документированный fallback
   updatedAt/createdAt/updateTime. Историческую точную дату, если её нет, не выдумывать.
4. Пересчитывать и записывать проекцию в транзакции, согласованной с одновременной записью
   оценки. Все чтения перед записями; конфликты повторяют расчёт, а не старый payload.
5. Repair по умолчанию выполняет dry-run, требует точного списка ID для apply, повторно
   читает данные перед записью и сохраняет только разрешённые производные поля через merge.
6. Для восьми фильмов сохранить существующие метаданные; для отсутствующего документа
   восстановить метаданные отдельно по точному KP ID. Сбой провайдера не отменяет агрегаты:
   временный заголовок/постер допускается, исключение оценённого фильма из списка — нет.
7. После записи прочитать документы заново, сверить расчёт и выполнить запрос страницы.
   Повторный запуск должен дать zero changes; отсутствие изменений не обновляет даты.

Готово: восемь фильмов появляются, суммы и даты корректны, ни одна оценка не изменена.
Откат: восстановление только затронутых полей при совпадении ожидаемого updateTime;
если после ремонта пришли новые оценки, заново пересчитать, а не затереть свежие данные.

## 4. Этап C — исключить гонки и опасную очистку на сервере

Файлы: `functions/index.js`, `functions/ratingProjectionService.js`, тесты агрегатора.
Почему: повторный запуск триггера не должен записывать устаревший результат или удалять
фильм на основании снимка, сделанного до появления новой оценки.

1. Триггер делегирует общему сервису и всегда читает актуальное состояние; event payload
   используется для определения затронутых ID, а не как полная база для арифметики.
2. Проверить в эмуляторе: A прочитал старый набор, B изменил оценку и завершил пересчёт,
   A продолжил. Итог обязан соответствовать актуальному набору, включая пустой результат.
3. На нуле оценок записывать согласованные нулевые агрегаты и false-флаги, сохраняя
   метаданные. Не удалять movie-документ в обычном триггере рейтинга.
4. `cleanupUnratedMovies` проверяет реальное отсутствие эффективных оценок в транзакции,
   а не доверяет отсутствующему hasCommunityRating. Dry-run не пишет вообще ничего.
5. Старый `backfillMovieAggregates` перевести на общий сервис, ограничить область и
   добавить проверку администратора на уровне обработчика. Не запускать старый endpoint
   как быстрый ремонт: сейчас его подсчёт расходится с дедупликацией агрегатора.
6. Ошибки пересчёта не поглощать; включить ограниченные повторные попытки и сигнал
   оператору. Не вводить бесконечный цикл самозапуска на запись тех же полей.

Готово: поздние события, повторная доставка и параллельное удаление/создание оценки
не оставляют неверные агрегаты. Метаданные и рейтинговая целостность разделены по правам.

## 5. Этап D — совместимый переход на серверное сохранение

Файлы: новый `functions/ratingWriteService.js`, wiring в `functions/index.js`,
`src/shared/services/RatingService.js`, `src/shared/config/rating.config.js`,
тесты rating-review и rating-uniqueness. Расширять имеющийся сервис, не создавать
параллельный клиентский RatingService и не добавлять второй механизм повторных записей.

1. Серверный save/delete принимает movieId, изменение пользователя, requestId и
   ожидаемую ревизию. uid берётся из проверенного токена, approval — из серверного профиля.
   Никогда не принимать client-supplied uid, count, sum, average или роль администратора.
2. В одной транзакции сохранить/удалить авторскую оценку и пересчитать movie-проекцию.
   Повторный requestId возвращает прежний результат; устаревшая ревизия не затирает
   более новую правку. Конфликт возвращает явную ошибку для обновления формы.
3. Сохранять разницу между отсутствующим полем review и явным его очищением. Изменение
   только текста не двигает числовую дату. Другие авторы и их записи недоступны для записи.
4. Ответ содержит подтверждённую оценку, агрегаты и ревизию. Клиент показывает успех
   только после подтверждения; при сбое сохраняет ввод и даёт повторить запрос с тем же ID.
5. Не возвращаться к прямой записи в Firestore после сетевой ошибки нового endpoint.
   Иначе повторный запрос и fallback могут применить две разные операции.
6. Release A: сначала серверный endpoint при прежних разрешениях; затем новый клиент.
   Старые версии ещё работают, но окно совместимости не считается окончательной защитой.
7. До cutover проверить реальную новую сборку: создание, редактирование, удаление,
   отзывы, избранное и отсутствие сети. Передать пользователям требование обновления.
8. Release B: запретить клиентские записи агрегатов и прямые save/delete оценок,
   перенесённые на сервер. Если избранное пока меняет rating-документ, разрешить только
   точный список его полей либо перенести эту операцию; не сломать её общим запретом.

Готово: все поддерживаемые версии используют новый путь; неподдерживаемая версия
не может повредить проекцию и не сообщает ложный успех. Без явного cutover гарантия
совместимости старого прямого writer и полного запрета повреждения невозможна.

## 7. Этап F — автоматическая сверка и наблюдаемость

Файлы: новый `functions/ratingIntegrityService.js`, wiring scheduler в `functions/index.js`,
тесты сверки. Этот модуль координирует обход, но не имеет собственного алгоритма расчёта.

1. Обходить ratings с курсором, нормализацией ID и общим правилом эффективной оценки.
   Пустой результат страницы не принимать за успешную сверку, если запрос завершился ошибкой.
2. Проверять соответствующие movies и поля сортировок. Отсутствие name не должно
   молча исключать фильм при сортировке по названию; metadata repair учитывает и это.
3. Ввести небольшие лимиты чтения/исправления и время выполнения; сохранять continuation
   cursor до завершения полного цикла. Публиковать fullScanCompleted отдельно от runsSucceeded.
4. Начальная частота — один полный цикл в сутки; dry-run перед включением auto-repair.
   Частоту и бюджет уточнить по измеренному числу чтений. Начальная цель: обнаружение
   исторического дрейфа за 24 часа при успешном завершении цикла.
5. Automatic repair — только производные поля через общий транзакционный сервис;
   не удалять ratings, не менять отзывы, не запускать очистку по итогам сверки.
6. Логировать runId, число проверенных ID, типы нарушений, repaired/failed/conflicts,
   duration, reads, continuation и возраст последней полной сверки. Без текстов отзывов.
7. Сигнализировать о любом неустранённом расхождении, провале повторных попыток и
   отсутствии полного цикла более 26 часов. Здоровые запуски не создают шумных уведомлений.

Готово: тестовая порча только movie-проекции исправляется без новой оценки; повторный
запуск не пишет; отключение/ошибка задания становится видимой, а не выдаёт false success.

   Протестировать изменение сортировочного ключа между страницами, dedup ID и перезагрузку.
4. Добавить build fingerprint и версию write-протокола в диагностику. Хеш исходников
   должен учитывать незакоммиченные изменения; один git commit или manifest недостаточен.
5. Existing missing-timestamp fallback оставить временно. Удалять отдельным небольшим
   изменением после cutover, нулевых нарушений и тестов всей пагинации; не расширять
   fallback до полного чтения ratings на каждом открытии страницы.

## 9. Матрица обязательных тестов

| Сценарий | Ожидаемый результат |
|---|---|
| Оценки есть, movie отсутствует | Repair создаёт проекцию; ratings неизменны |
| Movie есть без всех агрегатов | Repair возвращает его в запрос страницы |
| Флаг false при существующих оценках | Исправление по реальным оценкам |
| Нет даты или имени сортировки | Диагностика и исправление; карточка не теряется |
| Numeric/string ID, дубли автора | Тот же результат, что у canonical selector |
| Изменение только review/comment | Числовые агрегаты и их дата не меняются |
| Повторный requestId / потерянный ответ | Нет двойного применения |
| Две одновременные оценки | Count/sum/average соответствуют обеим |
| Запоздалый триггер | Свежая проекция не перезаписана старой |
| Удаление последней оценки + новая оценка | Новый рейтинг и movie сохраняются |
| Cleanup + новая оценка | Нельзя удалить активную проекцию |
| Старый клиент: delete или full set | Запрет после cutover |
| Metadata merge | Агрегаты и даты сохранены |
| Прерванный цикл сверки | Возобновление, не ложный zero mismatches |
| Repair параллельно новой оценке | Повторный расчёт/конфликт, без потери новой записи |
| Неполный провайдер метаданных | Оценённый фильм остаётся доступен |
| Холодный/тёплый кэш, несколько вкладок | Согласованный подтверждённый результат |

## 10. Порядок внедрения, откат и критерии завершения

1. A: снимки, аудит и проверка опубликованных компонентов.
2. B: проверенный общий расчёт и точечное восстановление; read-back всех восьми ID.
3. C: серверные гонки, cleanup и безопасный backfill.
4. D/Release A: endpoint, затем совместимый клиент и проверка реальной установки.
5. E + D/Release B: закрытие старых writers после готовности клиента.
6. F: dry-run сверки, затем bounded auto-repair и сигналы о сбое.
7. G: проверка UI/кэшей и диагностики; финальная полная сверка.

При регрессии нового клиента откатывать его к совместимой серверной ревизии, не к
старому прямому writer после cutover. Не восстанавливать широкое allow write как
обычный rollback. При сбое scheduler отключить только auto-repair, оставить dry-run
и защиту записи. При конфликте снимка данных не выполнять слепой restore.

Критерии завершения:

- Все восемь фильмов доступны без повторного выставления оценок.
- Полная сверка показывает ноль необъяснённых нарушений; неправильные исторические
  строки либо явно классифицированы, либо исправлены отдельным утверждённым действием.
- Эмулятор доказывает запреты старых writers и устойчивость конкурентного пересчёта.
- Создание, редактирование, удаление, review, comment и избранное работают в новой сборке.
- Наблюдение после внедрения охватывает минимум семь полных суточных циклов без дрейфа.
- Журналы позволяют отличить повреждение, отставание задания, сетевую ошибку и старую сборку.

Нельзя обещать абсолютное отсутствие любых будущих сбоев. Итоговая защита должна
предотвращать известные механизмы, обнаруживать нарушения и автоматически восстанавливать
производные данные без потери пользовательских оценок.

## 11. Самопроверка плана и границы исполнения

- Только восстановление данных недостаточно: старые writers и гонки могут повторить сбой.
- Только запрет правил недостаточен: Admin SDK их обходит, сервер тоже должен быть безопасен.
- Только обновление клиента недостаточно: другие установки продолжают писать в общую базу.
- Только scheduler недостаточен: между циклами страница всё равно будет неполной.
- Только тест сортировки недостаточен: текущий тест прошёл при восьми повреждённых фильмах.
- Новый server write path оправдан атомарным владением; новый алгоритм дедупликации не нужен.
- `functions/index.js` сохраняет wiring, новые обязанности выносятся в узкие модули.
- Старые клиентские агрегаты, опасный cleanup и самостоятельный backfill выводятся из
  эксплуатации по этапам; отзывы и оценки не входят в трек удаления.
- Исполнение последовательное, с проверкой после каждого этапа; текущая задача ограничена планом.
- Документы проекта обновляются по факту внедрения, а не описывают предлагаемые модули
  как уже существующие. README сейчас фиксирует только создание плана.
