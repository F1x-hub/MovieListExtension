# Роль «Управляющий» для приватной watch-room — спецификация

## Цель

Создатель приватной staging-комнаты может назначить единственному приглашённому
участнику роль «Управляющий». Управляющий синхронно для всей комнаты запускает,
ставит на паузу и перематывает выбранное видео. Он не меняет источник, фильм,
код приглашения, участников или роли. Зритель остаётся ролью по умолчанию.

## Зафиксированная модель прав

| Роль | Play / pause / seek для комнаты | Смена источника | Приглашение и роли |
| --- | --- | --- | --- |
| Создатель (`owner`) | Да | Да | Да |
| Управляющий (`controller`) | Да | Нет | Нет |
| Зритель (`viewer`) | Нет | Нет | Нет |

Комната по-прежнему имеет максимум двух участников, поэтому в одной комнате
возможен только один `controller`: создатель и один приглашённый пользователь.
Роль `owner` неизменяема через UI и endpoint. Приглашённый пользователь сначала
всегда входит как `viewer`.

Зритель может нажать нативные кнопки своего плеера локально, если провайдер их
не позволяет скрыть, но его действие не записывается в общее состояние и
текущая синхронизация возвращает его к состоянию комнаты. Этот релиз не вводит
DOM-блокировку сторонних плееров.

## Владение и поток данных

Не создаётся новая коллекция, RTDB-ветка или постоянный listener.

1. Создатель открывает список участников и у приглашённого выбирает
   «Разрешить управление» или «Сделать зрителем».
2. Клиент вызывает существующий `watchRoomsStaging` с action `setMemberRole`.
3. Server-only `WatchRoomService` проверяет: actor — владелец комнаты, target —
   существующий не-владелец этой же неистёкшей комнаты, новая роль —
   `viewer` либо `controller`.
4. Сервер обновляет Firestore member-документ и одной RTDB multi-location
   записью зеркалирует `roomAccess/{uid}/{roomId}/role` и
   `roomLive/{roomId}/members/{uid}/role`. Presence остаётся индикатором
   онлайн-статуса, а не источником прав; его `role` обновится при следующем
   штатном переподключении без отдельного RTDB read.
5. Уже подписанный `membersRef` обновляет список. Контроллер узнаёт свою роль
   по собственной записи в этом snapshot; дополнительных Firestore read или
   RTDB listener не появляется.
6. При `owner` или `controller` telemetry play/pause/seek пишет следующий
   revision общего `state`. `providerHint` по-прежнему пишет только `owner`.

## Безопасность

- Клиент не получает права изменять membership или ACL напрямую: ветки RTDB
  остаются server-only.
- RTDB rules разрешают timeline-поля (`revision`, `phase`, `basePositionMs`,
  `effectiveAtMs`, `updatedBy`) только `owner` или `controller` с действующим
  `roomAccess` и approval-gate.
- `providerHint` остаётся owner-only.
- `updatedBy` обязан совпадать с Firebase Auth UID; rules продолжают требовать
  монотонный revision и действующий expiry.
- Endpoint отвергает попытки изменить владельца, назначить произвольную роль,
  повысить самого себя или изменить чужую/истёкшую комнату.

## Стоимость

Обычное воспроизведение не получает новых запросов. Одно ручное изменение роли:

- один HTTP Cloud Function request;
- ограниченная серверная проверка комнаты и target member;
- одна Firestore member-запись;
- одна RTDB multi-location запись.

При двух участниках отсутствует fan-out и нет polling, presence-документов,
истории действий или дополнительных scheduled-задач.

## Изменяемые владельцы

- `functions/watchRoomService.js` — canonical server authorization и mutation.
- `functions/watchRoomsStaging.js` — allow-list и request validation для action.
- `functions/index.js` — только если handler wiring потребует новый dependency;
  schedule cleanup не изменяется.
- `rules/database.rules.json` — права timeline для `controller`, без расширения
  source/content полей.
- `src/shared/services/WatchRoomStagingController.js` — единый helper
  `canControlTimeline()` и обновление локальной роли по members snapshot.
- `src/pages/movie-details/movie-details.js` и HTML/CSS списка участников —
  owner-only назначение роли и подписи ролей.
- Существующие тесты handler/service/rules/controller/UI расширяются
  позитивными и негативными контрактами.

## Acceptance criteria

1. После назначения управляющий запускает, ставит на паузу и перематывает —
   создатель видит изменение, состояние имеет корректный revision и `updatedBy`.
2. Зритель не может записать timeline в RTDB.
3. Управляющий не может изменить источник или роль любого участника.
4. Создатель может отменить право, после чего следующий action управляющего не
   меняет общее состояние.
5. Перезагрузка комнаты не сохраняет клиентскую сессию; участник снова входит
   по активному коду и получает server-side роль.
6. Смена роли добавляет только описанные редкие записи и не меняет ежедневную
   очистку, TTL, лимит двух участников или one-time invite.

## Проверка

- service/handler: actor/target/expiry/role allow-list и RTDB mirror;
- rules: `controller` может менять только timeline-поля, но не `providerHint`;
- controller: promotion/demotion меняют право публикации telemetry;
- MovieDetails UI: owner видит действие только для второго участника, остальные
  пользователи видят лишь текущую роль;
- два браузера: назначение → play/pause/seek → отзыв роли → отклонённый write;
- `npm run lint`, focused room tests, `npm run build`, `git diff --check`;
- deploy только изменённых function/rules после локального прохождения тестов.

## Не входит в релиз

- Передача владения, кик, чат, голос, публичные комнаты, больше двух участников.
- Смена фильма/источника управляющим.
- Постоянное хранение сессии после reload.
- Попытка скрывать/перехватывать нативные элементы управления каждого внешнего
  провайдера.
