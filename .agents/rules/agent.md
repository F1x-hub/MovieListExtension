## Project
A powerful Chrome Extension (Manifest V3) that enhances the movie discovery and viewing experience. It provides movie rating syncing, Kinopoisk/IMDb integrations, automated player cleanups, custom HLS streaming injections, offscreen audio streaming, and seamless Firebase Firestore database synchronization.

## Architecture

- **Windows updater boundary**: `UpdateService` owns update state and user-visible
  status in the extension. `com.movielist.updater` is a separate Native Messaging
  host; it validates signed release metadata, downloads and stages ZIPs, replaces the
  configured unpacked directory through one temporary recovery directory, and confirms
  activation before cleanup. Setup and apply mutations use named locks, stale journals
  are recoverable, a one-shot `HKCU\...\RunOnce` entry protects interrupted
  replacement only, and older Setup binaries cannot downgrade the installed updater.
  Manual updates require explicit confirmation when playback is detected; automatic
  updates wait for a safe moment. Inaccessible third-party tabs are not treated as
  active media. The service worker closes open extension-owned pages before the
  native host moves the unpacked directory and synchronizes native operation state
  before settings renders a pending update. It never accepts shell commands or an
  arbitrary destination path from the extension. Chrome and Edge user-level Native
  Messaging registrations point to the same permanent host executable.
  Native directory moves create the destination parent before replacement; real
  filesystem replacement and recovery are tested in native-host/Updater.Tests.
  Signed release metadata requires Native Host 1.1.4 or newer and directs users with
  older hosts through a one-time Setup migration.
  Activation reload runs only after native replacement reaches awaiting_confirmation;
  UpdateService stores up to 500 diagnostic events and exports them from settings;
  diagnostics exclude metadata bodies, signatures and signed URL query parameters.
  Metadata transport failures make three total attempts per source with a Firebase fallback; ZIP reads have a 30-second idle timeout
  and a ten-minute total deadline. Failed checks are displayed in settings.
  every state reconciliation triggers activation and polling ends after confirmation.
- **Watch-room staging proof**: `watchRoomsStaging` is an authenticated Cloud Function backed by server-only `watchRoomsStaging*` Firestore collections and the isolated `watchrooms-staging` RTDB target. It creates private rooms for 10 total participants, uses one shared invite with 9 guest redemptions, and mirrors membership ACLs plus sanitized display names before clients subscribe. Staging suppresses its unused Firestore ACL outbox because the endpoint performs the RTDB mirror synchronously. Room creation is idempotent per authenticated actor and request ID through a server-only create-request ledger; expired-room cleanup removes that ledger with the bounded room documents. `cleanupExpiredWatchRoomsStaging` is a separate daily `04:15 Asia/Tbilisi` scheduled function that queries only expired staging rooms, caps every run at 50 rooms, accepts up to 10 member documents, one shared invite document, and one create-request document, removes RTDB live/room-ACL branches before the bounded Firestore room/member/invite/request set, and retries once on failure; expiry rules remain the access boundary. The durable room member role is server-owned: the owner can grant/revoke a member's `controller` role through `setMemberRole`, then one RTDB root update mirrors the role paths. Owner and controller publish and apply the existing play/pause/seek state, while audio tracks, subtitles, quality, volume, and speed remain local. Room `effectiveAtMs` values are estimated server time (`Date.now()` plus `.info/serverTimeOffset`), never a raw participant clock. Followers seek only outside a 1 s playing / 0.3 s paused tolerance; periodic `timeupdate` samples drive drift correction (two confirmations, 4 s cooldown), and the publisher of the current state re-anchors the room after its own playback slips. Drift is corrected by seeking only, never by changing playback speed. Player events caused by a room command are consumed by matching the commanded seek target or phase, with the 1.2 s window only as a fallback. Series rooms share `state/selection` (`seasonNumber`, `episodeNumber`; owner and controller write it, RTDB validates it): `PlaybackController.onSelectionChange` publishes it, followers open it through `playSelection()` and apply the timeline only after the new player reports readiness (15 s timeout without retry), and the owner seeds it when a room has none. Members leave through the existing `leave` action; the owner ends the room through `end`, which marks it `ended` with `expiresAt` set to now and removes `roomLive/{roomId}` plus every member's `roomAccess` entry. Invite codes are `<kinopoiskId>:<inviteId>.<secret>`; the client checks the film before redeeming and sends only the server part. The movie page keeps its room in `sessionStorage` (`movieExtensionWatchRoomSessionV1`) and rejoins through the idempotent `join` when the player container reaches `data-source-state="ready"`; a 4xx answer forgets it. `callApi` maps server error codes to Russian messages (`watchRoomErrorMessage`). Room play/seek commands wait for `ROOM_SYNC_COMMAND_RESULT` (8 s); `PLAYBACK_BLOCKED` raises `onPlaybackBlocked` for the "Включить просмотр" button, whose click calls `resumeBlockedPlayback()`. A rejected state write re-applies the room state locally. Followers get short notes for another member's pause, resume, episode switch, or seek of at least 10 s; smaller jumps are treated as drift re-anchors and stay silent. The owner extends a room through `extend` (+2 h per call, capped at 12 h after creation, `ROOM_EXTENSION_LIMIT` beyond); the server moves every member's `roomAccess/{uid}/{roomId}/expiresAtMs`, which clients watch to re-arm their expiry, and members get `onExpiryWarning` 10 minutes before closing. Members write `readiness/{uid}` (`resolving`/`ready`) from `waiting`/`playing`/`canplay` telemetry after a 1.5 s stall; the timeline publisher pauses the room for online loading members and resumes at the same position when they are ready or after 20 s, with a 60 s per-member cooldown; a manual action or another member's state cancels the wait. `WatchRoomStagingController` supports iframe and direct native-video mounts, preserves the existing provider-switch and timeline contracts, and writes canonical per-tab `presenceV2/{uid}/{connectionId}` records with strict RTDB rules; the legacy flat `presence/{uid}` path is read-compatible only. Presence uses child listeners, `onDisconnect().remove()`, a 30-second RTDB-only heartbeat, a 90-second stale threshold, and `.info/connected`; transient network loss preserves the room and never calls Firestore `join`. `callApi` preserves HTTP status and backend error codes so terminal `409` capacity/invite errors are not retried as network failures. On room expiry or server deletion the controller detaches local listeners and UI while the server cleanup removes the live RTDB branch. After a full page reload the tab rejoins its saved room automatically (same tab only); a transient RTDB reconnect does not require a new invite.

Active per-key registry tokens are selected server-side and never sent to the extension client; the legacy `TMDB_API_TOKEN` deployment secret is a migration-only bridge when no TMDB registry record exists.

Raw credentials live in per-key Secret Manager versions; Firestore stores only safe metadata and immutable audit records. Kinopoisk quota comes from its non-billing `GET /v1.5/token` contract (`requestsLimit`, `requestsUsed`, `requestsRemaining`); the admin header shows this exact daily total separately from TMDB, which validates with `GET /3/authentication` but does not publish a daily remaining count. `providerKeyPool` loads active entries with bounded TTL caching, while aggregate/legacy deployment secrets remain rollback bridges until an explicit retirement.

Modal chrome uses the neutral `--ui-*` tokens in both themes; boards, pieces and stickers keep their game colours.

They convert licensed OpenRussian vocabulary and Navec embeddings into a shared vocabulary plus per-puzzle uint16 little-endian Base64 rank tables, with a 90-day exact-date manifest; the embedding model is never loaded by the extension.

Admin-verified TMDB→Kinopoisk mappings are stored in Firestore (`tmdbKinopoiskMappings`) for authenticated readers, with `tmdbKinopoiskReverseIndex` as a transactional uniqueness lock. Local storage is a derived cache only, invalid shared records are rejected, and a confirmed cloud deletion evicts its derived cache entry.

The page manager owns filtering, selection locking, and the HTML detail panel.
- **Comment Reactions**: `CommentReactionService` stores up to three unique reaction types per user and rating in `commentReactions/{ratingId}_{userId}` using a Firestore transaction. `types` is canonical, while legacy scalar `type` remains a compatibility mirror for mixed client versions. The public `settings/commentReactions` document is the catalog source of truth; admins publish up to 24 labeled emoji definitions, including optional `renderType: image` assets uploaded to Firebase Storage through file selection, drag-and-drop, or Ctrl+V paste, while clients fall back to bundled defaults or the image shortcode when the document/assets are unavailable. Firestore Rules validate reaction IDs against that catalog and the reaction's `movieId` against its rating document; Storage Rules allow public reads and admin-only writes for validated PNG/WebP/GIF assets. `aggregateCommentReactions` rebuilds read-only `commentReactionSummaries/{ratingId}` documents from the active catalog; reaction writes never modify `ratings` and therefore never trigger movie rating aggregate recalculation. Movie Details and Search render the shared `CommentReactionBar` with optimistic updates, rollback, localized labels, busy-state locking, a collapsed, locally anchored viewport-aware picker, image fallback, and live catalog refresh.
- **Modular Error Presentation**: `src/shared/errors/` owns stable error codes, prioritized domain modules, normalization, and localized presentation. Pages pass structured errors to `errorDialog` through `Utils.createPageStateManager`; technical causes remain behind an explicit details disclosure. Blocking provider errors are localized through the shared `I18n` singleton, while transient toasts and external player noise remain separate.
- **Person Details Kinopoisk Enrichment**: `PersonDetailsService` keeps TMDB as the person metadata source, while `KinopoiskPersonHtmlService` reads the person page's embedded SSR Apollo state to merge native KP film IDs locally; every unique KP film ID is validated through exact-ID movie-page HTML with two-worker concurrency and a 30-day `kp_movie_poster_html_v3_{id}` cache, accepting only the page's `img.film-poster`, including self-healing of legacy cached person DTOs based on the authoritative `kp:{id}` route; cached DTO repair enriches both serialized `filmography` and separately serialized `knownFor` items; the HTML service is resolved lazily so deferred page-script order cannot disable enrichment; the existing `IdMappingService` batch remains the fallback when HTML is blocked or unusable.
- **Home TMDB-only discovery**: The active Home path uses `HomeCacheService` with `tmdbOnly: true`, stores TMDB-only cards under `home_discovery_cache_v14` (a usable legacy v13/v12 payload is served once, with resized posters, while v14 refreshes, then removed), and performs no Kinopoisk API mapping or catalog supplement during page load. `HomeMovieNavigationService` resolves missing KP IDs only after a card click through the browser-context Kinopoisk HTML search, deduplicates in-flight lookups, and stores verified results under `home_kp_html_mapping_v4` with KP/IMDb search metadata. Identity resolution never requires a search-card rating; when the rating is absent, `MovieRatingsEnrichmentService` uses a bounded public movie-page HTML fallback without the KP API. Negative Home mapping and card-rating records are provisional: legacy negatives without `retryAfter` are stale, and new negatives retry after a bounded 15-minute interval. `MovieRatingsEnrichmentService` separately parses IMDb `/find/` HTML for the IMDb ID and rating without an IMDb API quota. Rating-required offscreen KP searches carry an explicit flag and wait for result-card hydration before returning, because search links can render before numeric ratings. TMDB-only Home clicks immediately open an internal `resolveTmdbId` details route with a visible loader; that route performs the HTML mapping and replaces itself with the canonical movie route. The canonical Home route passes `tmdbId` and `source=home-tmdb-only` to `MovieDetails`; `MediaAggregatorService` then skips the Kinopoisk API and builds the detail DTO from TMDB.
- **Search rendering pipeline**: `KinopoiskService` owns parse and order preservation; `SearchManager` waits for complete ordered entities, applies client filters, slices the ordered chunk, and appends cards only after posters and metadata are ready. Search generations and abort signals discard stale provider, rating, bookmark, and enrichment results. Personal ratings use `RatingService.getUserRatingsForMovies()` and bookmark controls use `FavoriteService.getBookmarksBatch()` so Firestore latency cannot block the ordered card render.
- **Search timing evidence**: `[SearchTrace]`, `[KinopoiskSearchTrace]`, `[KinopoiskOffscreenTrace]`, and `[KPScraperTrace]` share a `traceId` across the search pipeline. Keep `traceId` separate from `requestKey`, which remains the cache/deduplication identity.
- **Search loading state**: Keep `resultsGrid` non-empty during provider work with the accessible `.search-loading-state`; clear `aria-busy` when cards, an empty state, or an error state takes ownership. Firebase-manager startup is bounded to three seconds; collections load in the background and patch only the collection menu when late, while failure restores the interactive empty state without replacing an active or URL-driven search.
- **Recommendation performance**: Coalesce scraper DOM checks, start visible recommendations during idle time, mount cards as one fragment, and activate only near-viewport posters. Deferred MovieDetails poster activation uses a narrow 96px horizontal window so a short carousel cannot decode every large poster on initial paint. Similar-film parser work has one 3.5-second queue-and-service deadline before the fallback path. Keep `[KPScraperTrace]`, `[RecommendationRenderTrace]`, and `[RecommendationImageTrace]` metrics intact when changing this flow.
- **TMDB metadata & Recommendations Pipeline**: `TMDBService` provides structured queries for metadata, seasons, recommendations (`/movie/{id}/recommendations`, `/tv/{id}/recommendations`), and similar titles (`/movie/{id}/similar`, `/tv/{id}/similar`) with Bearer token rotation, localized Russian titles, and pagination. `RecommendationService` first attempts one quota-free Kinopoisk `/film/{id}/like/` or `/series/{id}/like/` browser parse, preserving source order and native film/series identity; parsed cards are normalized directly without per-card API lookups. If the parser is unavailable or yields fewer than four compatible items, TMDB recommendations remain the fallback and candidates are batch-mapped to Kinopoisk IDs via `IdMappingService.resolveBatch(candidates, { skipQueue: true, context: 'recommendations', fastPath: true })` with a bounded fallback budget. Results are filtered against explicit/adult content, self-identity, and semantic categories, normalized into `RecommendationDTO` objects, bounded to target 10, and cached in `chrome.storage.local` (`movie_recommendations_v1_{tmdbId}_{mediaType}`) with 14-day TTL and bounded LRU eviction (max 100). On `MovieDetails`, recommendations render asynchronously via `IntersectionObserver` and idle scheduling with skeleton cards, dynamic localized headings, a horizontal carousel, one-fragment mounting, near-viewport poster activation, strict deduplication, a minimum 4-card viability threshold, and `[RecommendationTrace]`/`[RecommendationRenderTrace]` timings; the legacy `SimilarMoviesParsingService` remains unused.
- **Interactive Franchise / Collection Pipeline**: Movies belonging to a franchise (`belongs_to_collection` / `movie.collection.tmdbId`) render an interactive lazy-loaded franchise carousel (`#movieFranchiseSection`) powered by `FranchiseService` (`src/shared/services/FranchiseService.js`) and `TMDBService.getCollection(collectionId)`. Initial page render mounts a lightweight skeleton placeholder with clean franchise title (`FranchiseService.cleanCollectionName` stripping redundant `(Коллекция)` suffixes). As the section approaches viewport (`IntersectionObserver`, `rootMargin: '300px'`), collection parts are fetched from TMDB `/collection/{id}` with localized Russian metadata, sorted chronologically by release date (`releaseDate ASC`, undated items at end), and filtered for non-adult and valid items. Collection parts are batch-mapped in a single call via `IdMappingService.resolveBatch(parts, { skipQueue: true, context: 'franchise' })`, keeping the unmapped queue pristine. Collections are cached in `chrome.storage.local` (`tmdb_collection_cache_v2_{id}`) with 14-day TTL, LRU index bounding (max 100 entries), and in-flight Promise deduplication (`inFlightRequests`). In the DOM, cards render in chronological order: the active movie is highlighted with `.franchise-card--current`, `aria-current="true"`, and a "Сейчас" badge (non-clickable); every verified `kinopoiskId > 0` renders as a canonical MovieDetails link regardless of release date; upcoming status only controls the "Скоро" badge; only unmapped parts are inert. After lazy resolution, stable KP identities (TMDB fallback when available on both sides) remove franchise overlaps from the already-rendered sequel/prequel strip without a page rerender; unique relations remain, empty relation sections are removed, and stale movie responses are discarded. Empty or single-part collections are removed cleanly from the DOM with 0 trace.
- **Media Aggregator & Unified DTO**: `MediaAggregatorService` (`MediaAggregatorService.js`) combines Kinopoisk and TMDB into a single legacy-compatible `UnifiedMovieDTO` preserving `kinopoiskId > 0` as the root system identifier. It enforces strict orthogonal separation of the `identity` contract (`status: "VERIFIED"|"UNVERIFIED"`, `verificationMethod`, `verificationSource`), provider metadata quality (`FULL`, `PARTIAL`, `DRAFT`, `EMPTY`, `UNAVAILABLE`), and field provenance (`_meta.fieldSources`). Exact `externalId.tmdb` matches auto-verify and remain immutable against downstream metadata drops, while heuristic matches require review. Ratings are isolated per provider (`rating.kp`, `rating.imdb`, `rating.tmdb`) without cross-contamination. Under Phase 1B, it preserves rich provider metadata without additional roundtrips: Kinopoisk facts (HTML-sanitized), critic ratings (`international` and `russian` with vote counts), logo URL, OTT watchability, and distributors; TMDB production companies (deduplicated & CDN-resolved), spoken languages, status, collection, credits, and YouTube videos (expanded via single-roundtrip `append_to_response: 'credits,release_dates,videos'`, priority-ranked trailers/teasers/clips, and bounded to max 20). Under Phase 1C, `MovieDetails` surfaces this preserved data with 0 additional network requests: YouTube video cards (max 6 with type badges, official badges, and lazy autoplay modal on click), compact production studios block with CDN logo fallbacks, deterministic Russian status translations with color-coded badges, franchise banner without fake links, interactive Facts tab with spoiler concealment and list toggles, percentage-scaled critic review scores in meta grid, and movie title logos with permanent title heading retention. Under Phase 1D, `MovieDetails` consolidates trailer delivery around `UnifiedMovieDTO.videos`: TMDB structured video is primary (pure `selectPrimaryTrailer` prioritizing Official Trailer > Official Teaser > Trailer > Teaser, localized RU > EN), KP structured trailer is secondary, and `TrailerParsingService` scraper is invoked strictly as an asynchronous fallback when structured videos are absent; warm-cache views and structured video loads execute with 0 scraper calls, 0 upfront iframes, and unified modal playback lifecycle. Any successful TMDB-only refresh removes the legacy caches. `[KPCardTrace]` goes through `_kpTrace` and logs only with the debug flag (errors always warn); `[KinopoiskSearchTrace]`, the per-search scraping log and the `[QuotaTracker]` table use the same page flag, while the background `[KinopoiskOffscreenTrace]` and the content-script `[KPScraperTrace]` use `chrome.storage.local.movielistDebugTraces === true`. `KinopoiskPersonHtmlService.findMovieByTitle(..., { reportFailure: true })` returns `{ failed, reason }` for technical failures (never cached); `HomeMovieNavigationService` then writes no negative mapping and enrichment retries after `searchFailureRetryMs` (2 minutes). `ImdbParsingService` shares its proxy back-off through `localStorage['movielist:imdb-ratings-proxy-unavailable-until']`, and enrichment skips TMDB `external_ids` while the proxy is unavailable. `homePageAuditRound3.test.cjs` runs discovery through the real `MediaClassifier`. `[MovieRatingsTrace]` on Home is enabled only by `localStorage['movielist:debug-ratings'] = '1'`.
- `MovieCard` English titles: in English mode a card shows `alternativeName`/`englishTitle` only when written in Latin script and never for TMDB-only cards, whose `name` already follows the interface language.

The scheduler remains the physical deduplication owner; service-level request consumers must not collapse requests before they reach it. Cache writes are serialized per service and use the browser Web Lock when available.
- **Auth Bootstrap & State Latching**: All components follow the "Optimistic Cache-First + Authoritative State Sync" pattern. `FirebaseManager` tracks `this.isAuthReady` and provides `waitForAuthReady(timeout)` to prevent lost events or premature "unauthenticated" guest renders on cold boot. `HomeDataController.ensureAuthReady()` acts as an explicit async barrier before rendering personal tiers. ## Visual Design System

The product visual language is **Yin-Yang / Obsidian-Zinc**: dark and light are
opposite poles of one neutral grayscale system. Colorful UI accents are not a
second design language and must not be added to individual pages.

- **Canonical source**: `src/shared/styles/tokens.css` owns semantic `--ui-*`
  roles. `theme.css` maps those roles for dark/light modes. Legacy variables in
  `common.css` and page-local tokens are compatibility aliases only; do not add
  new consumers or new visual owners.
- **Neutral UI chrome**: navigation, buttons, cards, tabs, filters, forms,
  modals, popovers, loaders, admin shell, page headers, focus states, and player
  controls use grayscale tokens, neutral alpha borders, and neutral shadows.
- **Theme symmetry**: dark and light themes use the same semantic roles with
  inverted contrast. `--theme-text-muted` is `#85858e` in dark mode and
  `#66666e` in light mode so regular subtle text remains at or above 4.5:1.
  Do not create a light-only or dark-only hue palette. Do not use low opacity
  as the only disabled-state cue or a legacy accent token for ordinary text.
- **Allowed color exceptions**: poster/photo content, provider or third-party
  brand marks, game boards/pieces, and essential semantic status may retain color.
  Status color must be paired with an icon, label, shape, or pattern and must not
  become decorative chrome.
- **Color ownership**: new hex/rgb/hsl values are forbidden in HTML, JavaScript,
  inline styles, or page CSS unless the value is a documented exception. New
  accent variables such as `--catalog-accent` or `--theme-accent` require an
  explicit design review and are normally rejected.
- **Migration guard**: `npm run test:visual-design` classifies every source
  stylesheet, checks theme-muted contrast, blocks retired decorative colors in
  migrated chrome, and rejects legacy generic popover variables. Update the
  classification and targeted guards whenever a stylesheet is added or moved.
- **Component ownership**: generic buttons, modals, dropdowns, menus, tooltips,
  popovers, cards, and player surfaces have one shared CSS owner. `.popover-surface`
  owns the scoped `--popover-surface-*` contract; do not restore legacy
  `--popover-bg`/`--popover-border` variables. Page styles may add only scoped
  layout, placement, density, or content variants.
- **Visual QA**: every UI change must be checked in dark and light themes at
  desktop and narrow widths. A task is not visually complete when a component
  works functionally but introduces a new palette, duplicate token, or cascade
  owner. See `docs/design-system.md` for the review checklist and exceptions.

PersonDetails DTOs expose independent `posterSource`/`hasArtwork` and `hasNavigationTarget` fields; TMDB items remain renderable when KP mapping is unresolved, and the cache namespace is `person_details_v2_*`. ## Key Conventions

- **Torrent modal layout**: Keep the video before the torrent workspace in DOM order.
  The video body owns vertical scrolling; the header cannot shrink. Explicit picker/play
  actions focus and scroll only that body; progress updates never scroll or stop monitoring.
  Search opens the release disclosure; successful playback collapses it without closing the panel.
  Verify viewport geometry with `node tests/torrentModalLayout.test.cjs`.

- Remux-first torrent playback: MovieDetails sends explicit browser HLS codec capabilities,
  including AV1/fMP4, to MediaPlayer. Never claim AV1 when MediaSource capability detection is
  unavailable. Send the same capabilities for new and saved-download playback sessions. The
  backend reports torrent progress separately from HLS-ready duration and
  pipeline state; the client uses HLS duration and a mode-aware startup buffer before autoplay.

- **Local service outage recovery**: Keep MediaPlayer transport health separate from
  torrent/download state. A connection failure or timeout must not reset a durable download;
  render retained progress as stale, suppress rate/peer/ETA claims, and use one token-guarded
  exponential-backoff owner for each download/progress poller. Abort obsolete in-flight requests
  during monitor teardown so an older request cannot clear newer monitor state. Reset to the
  normal interval after any successful service response.

- **Watch-room RTDB config**: `FirebaseManager` owns the public URL for the isolated staging RTDB in its Firebase client config. Do not restore an ignored runtime config file or point room flows at the default database; RTDB Rules, not URL secrecy, enforce access.
- **Comment-reaction transaction bootstrap**: Firestore Rules may allow `get` only for a missing canonical reaction ID ending in the authenticated UID, so the first reaction can start a transaction. Existing reaction documents remain readable only by their owner or an admin.
- **Watch-room auth and timer readiness**: `WatchRoomStagingController` waits up to ten seconds for Firebase Auth restoration before its initial create or join API request; do not reject a first click merely because the page rendered before Auth. Its default timer dependencies must call `globalThis.setTimeout` and `globalThis.clearTimeout` as Window methods, never store either method as an unbound callback.
- **Catalogue routing**: Home category links use `catalog.html?category=films|series|cartoons|anime`; legacy `search.html?type=...` links redirect to the canonical catalogue route. Do not resolve KP IDs for an entire list page; resolve them only through the existing click-time MovieDetails flow.
- **Card ratings**: `MovieCard` keeps KP, IMDb, and TMDB ratings in separate fields; compact badges must label the provider and never display TMDB as KP.
- **AnimeGo matching**: `AnimeGoParser.scoreCandidate` accepts exact titles (100), close containment (40), and equal word-stem sequences (`titleStems`, 90; Russian endings stripped from words longer than four letters, release qualifiers such as "(TV)" removed), then applies the year (+30 same, +10 one off, -40 otherwise; minimum 70). `findSeasonResult` first looks for a numbered season marker after the base title, then `findSubtitledSeasonCard`: base title + ":"/"." subtitle with the season's premiere year (`canonicalSeasons[].airYear` from TMDB season `airDate`), series kinds before OVA/specials/films and shorter titles first. `cachedSearch` keys include `seasonYear`.
- **Movie Details provider ratings**: `loadProviderRatingsInBackground` loads the hidden Kinopoisk movie page whenever a KP or IMDb rating (or a vote count) is missing, because that page is the working IMDb source while the `imdbRatings` proxy is unavailable. TMDB TV details request `external_ids` so TV titles carry an IMDb ID. The IMDb ID from the Kinopoisk page (or the card cache via `RatingsRefreshService.mergeRatingSources`) is set on the movie (`imdbId`, `identity.imdbId`, `externalId.imdb`) so `getProviderRatingUrl` can link; `persistCardRatingPatch` stores `imdbId` and `imdbCheckedAt` (creating a card-shaped `kp:<id>` record when absent), and a check within 12 hours suppresses another hidden page load for a title still missing IMDb data.
- **Card rating enrichment**: Home (including featured cards) and Catalog enrich only visible cards in the background, use direct KP IDs immediately and deduplicate title/year identity searches for cards without IDs, take the KP rating from the KP search result, read IMDb ratings for all pending cards in one request through the `imdbRatings` Cloud Function (`functions/imdbRatingsProxy.js`: validated title IDs only, IMDb GraphQL, 6-hour cache header; IMDb IDs from the KP result or TMDB `external_ids`), load the hidden KP movie page only while a provider is still pending (no KP rating, or IMDb not answered because the proxy is unavailable), and cache KP/IMDb results in `movie_card_ratings_v4`. Direct IMDb title pages (HTTP 202 bot challenge) and the IMDb suggestion API (no CORS) are not used for cards; `RatingsRefreshService` tries the proxy before the title page. A failed proxy is skipped for 10 minutes per page. KP search matching penalizes a film/series type mismatch and accepts a substring title only at >=60% length; rating-required offscreen searches wait for hydrated KP result-card ratings before returning. The observer uses a 40px root margin, processes at most 6 cards per flush, does not use per-card detail-page fallbacks after transient timeouts, and exposes `[MovieRatingsTrace]`, `[KPCardTrace]`, and `[KPScraperTrace]` diagnostics. Initial rendering must not wait for this work; partial records render KP immediately and keep IMDb in a provider-specific skeleton/pending state.
- **Naming**: camelCase for javascript files (`FavoriteService.js`), kebab-case for styling/HTML/folders (`movie-details`), and uppercase prefix for UI variables.
- **Code Separation**: Logic should be written in dedicated services in `src/shared/services/` and cached via caching services (e.g., `RatingsCacheService.js`).
- **Bundled game data**: Static game dictionaries belong under `src/shared/data/` and are loaded through a dedicated in-memory data loader; do not persist immutable rank data in `chrome.storage.local`.

Under Phase 4A & 4C, the subsystem maintains a strict two-layer architecture:

Continue-watching data is never shown on another user's profile. `applyViewerMode()` switches all viewer-addressed UI (edit action, continue watching, stat links, taste copy, tab title). `ProfileService` shares one ratings read (60 s memo) between the statistics and the paged recent ratings, and profile-page reads pass `throwOnError` so failures are not rendered as empty data. Local `profile_cache_{uid}` entries hold only rendered fields (`toCachedProfile`: no e-mail or admin/approval flags), are bounded to 20 through `profile_cache_index`, and are removed with the image cache on sign-out (`FirebaseManager.clearProfileCaches`). Profile-page avatar/banner uploads use versioned object names; the previous object is deleted only after the profile document points to the new one.
- **User Account Approval Lifecycle**: Newly registered user profiles receive `approvalStatus: 'pending'`. Legacy users are migrated to `approvalStatus: 'approved'`. Profile updates must preserve `approvalStatus` unless specifically updated via admin tools.
- **Auth Gate**: Every auth entry point (email login, registration, Google login, session restoration in `initializeUI` and `authStateChanged`) queries the user's Firestore profile. Users with `approvalStatus === 'pending'` or `'rejected'` are immediately signed out, local auth storage is purged, and dedicated Obsidian-Zinc approval status screens are displayed. Approved or legacy unmigrated users are granted access.
- **Firestore Security Rules**: Database writes to ratings, watchlist, watching, favorites, collections, and movies require `isApprovedUser()`. Document creation in `users/{userId}` allows self-registration only with `approvalStatus: 'pending'` and `isAdmin: false`. User profile self-updates cannot modify `approvalStatus` or `isAdmin`, and changed public fields are validated (`isValidProfileFieldUpdate`: safe `bannerURL`, `username` of 3–20 `[A-Za-z0-9_]` with a matching `usernameLower`, name/bio lengths, `displayNameFormat`). A user reads their own profile at any approval state; other profiles, which include `email`, are readable only by approved users and admins. Admins retain full authority to modify any profile fields. Storage `avatars/` and `banners/` accept only owner uploads of PNG/JPEG/WebP/GIF up to 5 MB.
- **Comment reaction security**: Clients may write only their own allowlisted reaction using the deterministic reaction document ID. Reaction summaries are public read-only derived state and are writable only by Cloud Functions/Admin SDK.
- **Admin Approvals & User Status Management**: The admin panel manages registration requests in a dedicated Approvals queue pane with real-time pending counter, batch approval, and individual approval/rejection. The users list displays approval status badges and allows filter by status (All, Approved, Pending, Rejected). Admins have bidirectional control over any user's status (approved <-> rejected <-> pending).
- **Auth & Popup Design**: Strict Obsidian-Zinc design tokens, 400x520px action-popup frame with intrinsic document/body minimum dimensions, internal auth/feed scrolling and an available-space side-panel variant (`popup-document--sidepanel` and `popup-page--sidepanel`) that releases those minima. Keep action-popup sizing independent of its initial viewport. Use monochrome CTA buttons, light/dark theme variables (no hardcoded color hexes), native navigation links and click handlers, `aria-label`/`aria-pressed` for password toggles, `aria-describedby`/`aria-invalid` field validation, and semantic readonly inputs for Step 2. Closed controls use hidden/inert; popup dialogs use shared modal surfaces, labels, focus containment/restoration and retryable errors. Approval read failures keep content blocked and offer retry.
- **Mobile fixed controls**: Fixed report controls must use a narrow-screen safe area and must not overlap protected-state alerts or other primary feedback.
- **Popup Feed Infinite Scroll & User Filtering**: `#infiniteScrollTrigger` remains inside `#feedContent`, and `IntersectionObserver` uses `root: this.elements.feedContent`. `RatingService.getAllRatings` supports optional `userId` and opt-in `throwOnError`; popup cache reads use the throwing path so outages do not become empty feeds. `RatingsCacheService` normalizes Kinopoisk IDs and repairs visible legacy metadata, retains the last successful page on failures, exposes a guarded `refreshPromise`, and serializes writes/clears with per-key request generations (`isSuperseded` results must be ignored). `MovieCacheService.getBatchCachedMovies` also reads legacy `kp_movie_*` localStorage metadata. Popup feed, search and auth generations reject obsolete responses; cards appear before optional averages, and background first-page refresh never removes appended pages. `MAX_CONSECUTIVE_AUTO_LOADS = 2` resets only on user wheel/touch/scroll-key input; failed pagination pauses with retry to protect quotas. Popup `user_profile_*` caches contain compact display fields only, are bounded by `user_profile_index` to 20, and join profile-page cache cleanup on sign-out.
