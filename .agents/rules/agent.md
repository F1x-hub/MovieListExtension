## Architecture

- **Watch-room staging proof**: `watchRoomsStaging` is an authenticated Cloud Function backed by server-only `watchRoomsStaging*` Firestore collections and the isolated `watchrooms-staging` RTDB target. It creates private two-person rooms, redeems one-time invites, and mirrors membership ACLs plus sanitized display names before clients subscribe; the function prefers the verified token name, then the signed-in extension profile name, then the token email prefix without an extra Firestore read. Staging suppresses its unused Firestore ACL outbox because the endpoint performs the RTDB mirror synchronously. `cleanupExpiredWatchRoomsStaging` is a separate daily `04:15 Asia/Tbilisi` scheduled function that queries only expired staging rooms, caps every run at 50 rooms, removes RTDB live/room-ACL branches before the bounded Firestore room/member/invite set, and retries once on failure; expiry rules remain the access boundary. The durable room member role is server-owned: owner can grant/revoke the invited participant's `controller` role through `setMemberRole`, then one RTDB root update mirrors only the two role paths. Owner and controller both publish and apply the existing play/pause/seek state, but each ignores their own echoed write; an owner applies a controller state directly without source remounting. The room bridge has an explicit three-command allow-list (`play`, `pause`, `seek`): audio tracks, subtitles, quality, volume, and speed are never stored in room state or applied remotely. Provider, invitations, membership and roles remain owner-only. `WatchRoomStagingController` supports both iframe bridges and direct native-video mounts, records a probed viewer's current provider before accepting room state so a matching initial source is not remounted, waits for native metadata before connecting, and treats the replacement player's `PLAYER_READY` signal as the canonical completion point for an iframe provider switch before applying the latest room revision. It retries an iframe probe until the video capabilities are ready, uses the existing native metadata wait for direct players, and expires an unconfirmed provider transition. Timeline writes are coalesced and serialized so every accepted update receives one monotonic RTDB revision. Presence arms `onDisconnect().remove()` before writing the record and may carry a bounded name from the browser's existing `userDisplayCache` or visible navigation profile; the explicit RTDB `displayName` rule permits that bounded value while `$other` rejects unapproved fields, and the member panel uses it only when an older membership record has the generic fallback. On room expiry or server deletion the controller only detaches local listeners and UI, keeping the existing disconnect registration because expired RTDB rules can reject a client mutation. The player modal owns a temporary copy-code status which clears after 2.5 seconds and keeps room counts only on the participants button. Its room buttons carry explicit action IDs and one container capture handler consumes the click before stale page-level listeners can misroute create and join after an extension reload. The iframe bridge must re-subscribe every replacement iframe and rebind telemetry whenever KinoGo replaces `permanentVideo`; otherwise the room remains subscribed to detached media. `RoomSyncTrace` logs only lifecycle stages, state-listener failures, and revision metadata in the browser console, never media URLs or room state into an extra database record. Room membership is session-scoped: after reload, a user joins again through an active invite. Provider adapters remain opt-in and expose no room-control capability by default.

## Visual Design System

The product visual language is **Yin-Yang / Obsidian-Zinc**: dark and light are
opposite poles of one neutral grayscale system. Colorful UI accents are not a
second design language and must not be added to individual pages.

- **Canonical source**: `src/shared/styles/tokens.css` owns semantic `--ui-*`
  roles. `theme.css` maps those roles for dark/light modes. Legacy variables in
  `common.css` and page-local tokens are compatibility aliases only; do not add
  new consumers or new visual owners.
- **Neutral UI chrome**: navigation, buttons, cards, tabs, filters, forms,
  modals, popovers, loaders, admin shell, page headers, focus states, and player
  controls use grayscale tokens, neutral alpha borders, and neutral shadows.
- **Theme symmetry**: dark and light themes use the same semantic roles with
  inverted contrast. `--theme-text-muted` is `#85858e` in dark mode and
  `#66666e` in light mode so regular subtle text remains at or above 4.5:1.
  Do not create a light-only or dark-only hue palette. Do not use low opacity
  as the only disabled-state cue or a legacy accent token for ordinary text.
- **Allowed color exceptions**: poster/photo content, provider or third-party
  brand marks, game boards/pieces, and essential semantic status may retain color.
  Status color must be paired with an icon, label, shape, or pattern and must not
  become decorative chrome.
- **Color ownership**: new hex/rgb/hsl values are forbidden in HTML, JavaScript,
  inline styles, or page CSS unless the value is a documented exception. New
  accent variables such as `--catalog-accent` or `--theme-accent` require an
  explicit design review and are normally rejected.
- **Migration guard**: `npm run test:visual-design` classifies every source
  stylesheet, checks theme-muted contrast, blocks retired decorative colors in
  migrated chrome, and rejects legacy generic popover variables. Update the
  classification and targeted guards whenever a stylesheet is added or moved.
- **Component ownership**: generic buttons, modals, dropdowns, menus, tooltips,
  popovers, cards, and player surfaces have one shared CSS owner. `.popover-surface`
  owns the scoped `--popover-surface-*` contract; do not restore legacy
  `--popover-bg`/`--popover-border` variables. Page styles may add only scoped
  layout, placement, density, or content variants.
- **Visual QA**: every UI change must be checked in dark and light themes at
  desktop and narrow widths. A task is not visually complete when a component
  works functionally but introduces a new palette, duplicate token, or cascade
  owner. See `docs/design-system.md` for the review checklist and exceptions.

PersonDetails DTOs expose independent `posterSource`/`hasArtwork` and `hasNavigationTarget` fields; TMDB items remain renderable when KP mapping is unresolved, and the cache namespace is `person_details_v2_*`. ## Key Conventions

- **Watch-room auth and timer readiness**: `WatchRoomStagingController` waits up to ten seconds for Firebase Auth restoration before its initial create or join API request; do not reject a first click merely because the page rendered before Auth. Its default timer dependencies must call `globalThis.setTimeout` and `globalThis.clearTimeout` as Window methods, never store either method as an unbound callback.
- **Catalogue routing**: Home category links use `catalog.html?category=films|series|cartoons|anime`; legacy `search.html?type=...` links redirect to the canonical catalogue route. Do not resolve KP IDs for an entire list page; resolve them only through the existing click-time MovieDetails flow.
- **Card ratings**: `MovieCard` keeps KP, IMDb, and TMDB ratings in separate fields; compact badges must label the provider and never display TMDB as KP.
- **Card rating enrichment**: Home (including featured cards) and Catalog enrich only visible cards in the background, use direct KP IDs immediately and deduplicate title/year identity searches for cards without IDs, prefer the hidden KP movie page for KP/IMDb ratings without opening visible tabs, use the legacy IMDb title-page parser only after a trusted IMDb ID is available, and cache KP/IMDb results in `movie_card_ratings_v4`; rating-required offscreen searches wait for hydrated KP result-card ratings before returning. The observer uses a 40px root margin, processes at most 6 cards per flush, does not use per-card detail-page fallbacks after transient timeouts, and exposes `[MovieRatingsTrace]`, `[KPCardTrace]`, and `[KPScraperTrace]` diagnostics. Initial rendering must not wait for this work; partial records render KP immediately and keep IMDb in a provider-specific skeleton/pending state.
- **Naming**: camelCase for javascript files (`FavoriteService.js`), kebab-case for styling/HTML/folders (`movie-details`), and uppercase prefix for UI variables.
- **Code Separation**: Logic should be written in dedicated services in `src/shared/services/` and cached via caching services (e.g., `RatingsCacheService.js`).
- **Bundled game data**: Static game dictionaries belong under `src/shared/data/` and are loaded through a dedicated in-memory data loader; do not persist immutable rank data in `chrome.storage.local`.
- **Rubik's Cube game**: Keep cube turns, solved-state checks, axis selection, and turn animation orchestration in `src/shared/games/RubiksCubeGame.js`; `GamesModal` only owns lifecycle, shared stats, overlay, and keyboard routing.
- **CSS**: Scoped class naming, CSS custom properties for theming (Light/Dark themes), and absolute responsive design layout.
- **Design tokens**: `src/shared/styles/tokens.css` is the canonical owner for semantic shared UI values; new components must consume `--ui-*` roles and must not introduce a local accent palette.
- **Shared buttons**: Generic `.btn` and shared semantic variants (`.btn-primary`, `.btn-secondary`, `.btn-accent`, `.btn-ghost`, `.btn-danger`) belong only to `src/shared/styles/components.css`; page-specific differences require explicit modifier classes.
- **Modal shells**: Generic `.modal-overlay`, `.modal`, `.modal-header`, `.modal-close`, `.modal-body`, and `.modal-footer` belong to `src/shared/styles/components.css`; pages may add only scoped modal variants such as `.collection-modal`.
- **Dropdown shells**: Generic `.custom-dropdown`, `.dropdown-trigger`, `.dropdown-list`, `.dropdown-option`, and arrow states belong to `src/shared/styles/components.css`; page-specific styling must be scoped, while `open` and legacy `active` states remain supported during migration.
- **Menu and overlay primitives**: Generic `.menu-item`, `.menu-icon`, `.tooltip-surface`, and `.popover-surface` belong to `src/shared/styles/components.css`; page styles may own only placement, density, and content-specific variants.
- **Movie action groups**: `.movie-actions-container` layout and icon alignment belong to `src/shared/styles/components.css`; page styles may own only explicit specialized actions such as admin announce.
- **Loading states**: Use the shared `app-loader` namespace from `common.css`; do not add new global `.spinner` or `.loading-spinner` variants.

Player volume/settings/episode-picker surfaces use the shared `.popover-surface`; `player-cleaner.js` may add only iframe-safe boundary styles and placement/density variants.

Expanding season details (`toggleSeasonEpisodes`) lazily queries `TMDBService.getSeasonDetails()` with in-flight deduplication and bounded caching, enforcing a single expanded season panel accordion invariant. Under Phase 4A & 4C, the subsystem maintains a strict two-layer architecture:
  1. *Layer 1 (Fast Volatile Resume)*: `ProgressService` (`viewing_progress_v1_{movieId}`) stores the single active `{ season, episode, timestamp, duration, completed }` updated every 15s. Drives the Continue Watching banner (`#seasonsContinueBanner`) and Generic Watch routing (`source: 'RESUME'`).
  2. *Layer 2 (Stable Completed History)*: `EpisodeHistoryService` (`episode_history_v1_{movieId}`) stores a compact per-series completed episode map (`{"1:1": { cAt: number, src: "AUTO_RELIABLE"|"MANUAL" }}`). Auto-completion is strictly asymmetric (only Seasonvar `RELIABLE` auto-writes history on edge completion; opaque/partial providers require manual toggle). Manual toggle (`data-action="toggle-episode-watched"`) updates history non-disruptively without resetting resume state.
  Episode cards render `.episode-card--watched` with `✓ Просмотрено` badge (`.badge-watched-episode`) and manual checkmark button (`.episode-card__watched-toggle-btn`). On rewatch, both `✓ Просмотрено` and resume progress bar + `[▶ Продолжить]` are rendered simultaneously. Season completion counters (`getSeasonCompletionStats`) render `${completedCount} / ${totalReleasedCount} просмотрено` excluding future unreleased episodes, and full-season checkmarks (`✓`) on completed season pills. Prior episodes are never falsely inferred as watched. Under Phase 4D, the Seasons UI adds real-time currently-playing indicators: `updateActiveEpisodePlayingState(selection)` surgically updates episode card DOM (no full re-render) when `PlaybackController` fires `onSelectionChange` or `onStateChange('closed')`; the active episode card gains `.episode-card--playing` (indigo border+glow), `.badge-playing-episode` with animated pulse dot, and `episode-card__play-btn--playing` (stop `■` icon, `Играет` label). Season pills show `N/M` progress counts (`.season-pill-progress`) for partially-watched seasons, and `.season-pill-btn--completed` (green border/active) plus `season-completed-badge` with progress bar on season card headers when a season has any completed episodes.

- **Profile Personal Dashboard**: `profile.html` keeps the existing profile summary as the stable entry point, then adds a responsive dashboard for the current user. Watching favorites come from `FavoriteService`, local resume state comes from `ProgressService`, and the UI renders up to three continue-watching links plus genre chips and a 1–10 rating distribution from `ProfileService`. Continue-watching data is never shown on another user's profile.
- **User Account Approval Lifecycle**: Newly registered user profiles receive `approvalStatus: 'pending'`. Legacy users are migrated to `approvalStatus: 'approved'`. Profile updates must preserve `approvalStatus` unless specifically updated via admin tools.
- **Auth Gate**: Every auth entry point (email login, registration, Google login, session restoration in `initializeUI` and `authStateChanged`) queries the user's Firestore profile. Users with `approvalStatus === 'pending'` or `'rejected'` are immediately signed out, local auth storage is purged, and dedicated Obsidian-Zinc approval status screens are displayed. Approved or legacy unmigrated users are granted access.
- **Firestore Security Rules**: Database writes to ratings, watchlist, watching, favorites, collections, and movies require `isApprovedUser()`. Document creation in `users/{userId}` allows self-registration only with `approvalStatus: 'pending'` and `isAdmin: false`. User profile self-updates cannot modify `approvalStatus` or `isAdmin`. Admins retain full authority to modify any profile fields.
- **Comment reaction security**: Clients may write only their own allowlisted reaction using the deterministic reaction document ID. Reaction summaries are public read-only derived state and are writable only by Cloud Functions/Admin SDK.
- **Admin Approvals & User Status Management**: The admin panel manages registration requests in a dedicated Approvals queue pane with real-time pending counter, batch approval, and individual approval/rejection. The users list displays approval status badges and allows filter by status (All, Approved, Pending, Rejected). Admins have bidirectional control over any user's status (approved <-> rejected <-> pending).
- **Auth & Popup Design**: Strict Obsidian-Zinc design tokens, 400x520px fixed popup frame with internal scrolling in auth views, monochrome CTA buttons, responsive light/dark theme variables (no hardcoded color hexes), accessibility compliance (`click` handlers, `aria-label`/`aria-pressed` for password toggles, `aria-describedby`/`aria-invalid` field validation, semantic readonly inputs for Step 2).
- **Mobile fixed controls**: Fixed report controls must use a narrow-screen safe area and must not overlap protected-state alerts or other primary feedback.
- **Popup Feed Infinite Scroll & User Filtering**: `#infiniteScrollTrigger` sentinel element must be located inside `#feedContent`, and `IntersectionObserver` must configure `root: this.elements.feedContent`. `RatingService.getAllRatings` supports optional `userId` filter to scope recent ratings to the active account. `RatingsCacheService` normalizes numeric/string Kinopoisk IDs and repairs visible legacy cache entries that lack movie metadata before the popup renders them. `MovieCacheService.getBatchCachedMovies` also reads legacy `kp_movie_*` localStorage metadata when Firestore and `chrome.storage.local` do not contain a movie. `popup.js` enforces a defensive circuit breaker (`MAX_CONSECUTIVE_AUTO_LOADS = 2`, reset on user scroll event) and stops pagination on critical quota/403 errors to protect API keys and storage quotas.
